# MCU Bootloader 与多工程配置管理工程实战笔记

---

## 1. 架构背景与核心痛点

在基于 ARM Cortex-M（如 GD32F4xx / STM32F4xx）的高可靠性嵌入式设备中，**Bootloader（引导加载程序）** 与 **Application（业务程序）** 通常作为两个独立的工程进行开发与编译。

### 1.1 常见痛点

1. **多头维护，地址错位**：Bootloader 与 App 各自保留一份 `partition.h`，改动一边往往遗漏另一边，导致 App 入口地址与 Bootloader 跳转地址不匹配，设备启动即变砖。
2. **扇区边界未对齐**：随意划分分区地址，导致分区的起止位置落在某个 128KB 物理大扇区中间。在执行擦除或写入时，无意中抹除了相邻分区的数据。
3. **资源争抢**：带 GUI（如 LVGL）的产品如果把字体、高清图标等大量静态素材塞在片上代码区，会导致 2MB 的 Flash 空间迅速耗尽。

### 1.2 工业级解题规范

- **资源外置**：UI 图片、中文字库、大文件全部外放至低成本的 SPI/QSPI NOR Flash（如 W25Q128），通过 LittleFS 访问。
- **片内双区（A/B 分区）**：片内 2MB Flash 只存放纯机器执行代码，采用标准的 A/B 双备份高可用升级架构。
- **单一份源（Single Source of Truth）**：通过建立公共组件目录（`Common`），让两个独立工程利用**相对路径**共享同一份分区配置文件。

## 2. 2MB 双 Bank 物理扇区与分区映射

GD32F4xx / STM32F4xx 的 2MB 片上 Flash 采用标准的双 Bank 对称架构。分区起始地址与大小**必须严格对齐物理扇区起始边界**。

### 2.1 物理扇区与逻辑分区总览表

| 分区标识         | 逻辑起始地址 | 占用空间   | 物理扇区归属                                  | 单扇区物理尺寸                                               | 职能定义                                  |
| :--------------- | :----------- | :--------- | :-------------------------------------------- | :----------------------------------------------------------- | :---------------------------------------- |
| **Bootloader**   | `0x08000000` | **128 KB** | Sector 0 ~ 3<br>Sector 4                      | $4 \times 16\text{ KB}$<br>$1 \times 64\text{ KB}$           | 引导程序、固件搬运、通信下载协议栈        |
| **Boot Param**   | `0x08020000` | **128 KB** | Sector 5                                      | $1 \times 128\text{ KB}$                                     | 升级标志、CRC32 校验、固件版本、启动计数  |
| **App-A (主区)** | `0x08040000` | **768 KB** | Sector 6 ~ 11                                 | $6 \times 128\text{ KB}$                                     | 当前业务固件运行区（Bank 0 尾部）         |
| **App-B (备区)** | `0x08100000` | **768 KB** | Sector 12 ~ 15<br>Sector 16<br>Sector 17 ~ 21 | $4 \times 16\text{ KB}$<br>$1 \times 64\text{ KB}$<br>$5 \times 128\text{ KB}$ | OTA 固件下载暂存区 / 轮换运行区（Bank 1） |
| **User Data**    | `0x081C0000` | **256 KB** | Sector 22 ~ 23                                | $2 \times 128\text{ KB}$                                     | 业务数据持久化保存、日志记录或 LittleFS   |

> **容量核算**：$128\text{KB} + 128\text{KB} + 768\text{KB} + 768\text{KB} + 256\text{KB} = 2048\text{KB} = 2\text{MB}$。

## 3. 多工程目录架构与统一引用方案

### 3.1 目录组织树

```text
Project_Root/
├── Common/                      <-- 双方共享的单一源头
│   └── Inc/
│       ├── boot_partition.h     <-- 共享的 Flash 物理与逻辑分区定义
│       └── boot_param.h         <-- 共享的 OTA 升级元数据结构体
│
├── Bootloader/                  <-- Bootloader 源码目录
│   ├── Core/
│   ├── Drivers/
│   └── Project/                 <-- 存放 Keil (.uvprojx) 或构建脚本
│       └── bootloader.uvprojx
│
└── Application/                 <-- APP 业务源码目录
    ├── Core/
    ├── Drivers/
    └── Project/                 <-- 存放 Keil (.uvprojx) 或构建脚本
        └── application.uvprojx
```

### 3.2 构建环境配置方法

#### 方案 1：Keil MDK (ARM Compiler 5/6)

1. 分别在两个工程中按下快捷键 `Alt + F7` 打开 **Options for Target**。

2. 切换到 **C/C++**（或 **C/C++ (AC6)**）配置页。

3. 找到 **Include Paths**，点击 `...` 按钮。

4. 添加相对路径（以 `.uvprojx` 所在目录为起点）：

    ```text
    ..\..\Common\Inc
    ```

    *注意：禁止使用绝对路径（如 `D:\Code\...`），确保工程跨电脑无缝编译。*

#### 方案 2：GCC + Makefile / CMake

- **Makefile**：

    ```makefile
    C_INCLUDES += -I../../Common/Inc
    ```

- **CMakeLists.txt**：

    ```cmake
    target_include_directories(${PROJECT_NAME} PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/../../Common/Inc
    )
    ```

## 4. 共享头文件核心实现 (`boot_partition.h`)

此文件放置在 `Common/Inc/boot_partition.h`，利用 C11 的静态断言（`_Static_assert`）对整个分区链条进行自动化编译期体检。

```c
#ifndef BOOT_PARTITION_H
#define BOOT_PARTITION_H

#include <stdint.h>

/* =========================================================================
 * 1. 片上 2MB Flash 整体空间
 * ========================================================================= */
#define FLASH_START_ADDR        0x08000000U
#define FLASH_TOTAL_SIZE        (2048U * 1024U)                         /* 2 MB */
#define FLASH_END_ADDR          (FLASH_START_ADDR + FLASH_TOTAL_SIZE)   /* 0x08200000 */

/* =========================================================================
 * 2. 逻辑分区基地址与容量 (严格与物理扇区对齐)
 * ========================================================================= */

/* [分区 1] Bootloader 引导区 (Sector 0 ~ 4) */
#define PART_BOOT_ADDR          0x08000000U
#define PART_BOOT_SIZE          (128U * 1024U)                          /* 128 KB */

/* [分区 2] Boot Param 参数区 (Sector 5, 独立 128KB 扇区) */
#define PART_PARAM_ADDR         0x08020000U
#define PART_PARAM_SIZE         (128U * 1024U)                          /* 128 KB */

/* [分区 3] App-A 业务运行主区 (Sector 6 ~ 11, Bank 0 尾部) */
#define PART_APP_A_ADDR         0x08040000U
#define PART_APP_A_SIZE         (768U * 1024U)                          /* 768 KB */

/* [分区 4] App-B 下载备份区 (Sector 12 ~ 21, Bank 1 对称空间) */
#define PART_APP_B_ADDR         0x08100000U
#define PART_APP_B_SIZE         (768U * 1024U)                          /* 768 KB */

/* [分区 5] 用户数据存储区 / LittleFS (Sector 22 ~ 23) */
#define PART_USER_DATA_ADDR     0x081C0000U
#define PART_USER_DATA_SIZE     (256U * 1024U)                          /* 256 KB */

/* =========================================================================
 * 3. 编译期静态断言安全校验 (防手抖改错地址)
 * ========================================================================= */
#define STATIC_ASSERT_PARTITION() \
    _Static_assert((PART_BOOT_ADDR + PART_BOOT_SIZE) == PART_PARAM_ADDR, "Boot & Param overlap/gap"); \
    _Static_assert((PART_PARAM_ADDR + PART_PARAM_SIZE) == PART_APP_A_ADDR, "Param & App-A overlap/gap"); \
    _Static_assert((PART_APP_A_ADDR + PART_APP_A_SIZE) == PART_APP_B_ADDR, "App-A & App-B overlap/gap"); \
    _Static_assert((PART_APP_B_ADDR + PART_APP_B_SIZE) == PART_USER_DATA_ADDR, "App-B & UserData overlap/gap"); \
    _Static_assert((PART_USER_DATA_ADDR + PART_USER_DATA_SIZE) == FLASH_END_ADDR, "Flash total size mismatch")

/* =========================================================================
 * 4. 运行时防御性宏函数
 * ========================================================================= */
#define IS_IN_PARTITION(addr, part_addr, part_size) \
    (((uint32_t)(addr) >= (part_addr)) && ((uint32_t)(addr) < ((part_addr) + (part_size))))

#define IS_ADDR_IN_APP_A(addr)  IS_IN_PARTITION((addr), PART_APP_A_ADDR, PART_APP_A_SIZE)
#define IS_ADDR_IN_APP_B(addr)  IS_IN_PARTITION((addr), PART_APP_B_ADDR, PART_APP_B_SIZE)

#endif /* BOOT_PARTITION_H */
```

## 5. App 工程关键适配项

当 Bootloader 将控制权移交给 App 之前，App 必须配合完成两项底层适配：

### 5.1 链接脚本配置（修改运行起始地址）

- **Keil MDK**：
    进入 `Options for Target` -> `Target` 选项卡：

    - `IROM1 Start` = `0x08040000`
    - `IROM1 Size`  = `0x000C0000`（即 768 KB，写为十六进制）

- **GCC (`.ld` 链接脚本)**：

    ```ld
    MEMORY
    {
      FLASH (rx) : ORIGIN = 0x08040000, LENGTH = 768K
      RAM  (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
    }
    ```

### 5.2 中断向量表偏移（VTOR 重定位）

在 App 的 `main()` 函数第一行执行，确保中断产生时单片机能够从 App 分区获取正确的执行入口：

```c
#include "boot_partition.h"

int main(void)
{
    /* 1. 重定位中断向量表至 App-A 起始物理地址 */
    SCB->VTOR = PART_APP_A_ADDR;

    /* 2. 重新开启全局中断 (因为 Bootloader 跳转前执行了 __disable_irq()) */
    __enable_irq();

    /* 3. 正常执行时钟、外设初始化 */
    systick_init();

    while (1) {
        // App 业务逻辑
    }
}
```

## 6. 开发军规与避坑指南

1. **共享头文件严禁定义实体变量**：
    `boot_partition.h` 中只能包含宏定义、枚举、类型声明与 `static inline` 函数，不得定义全局实体变量，避免引起多工程符号冲突或未初始化变量。
2. **强制使用相对路径引用**：
    在工程配置（Include Paths）中绝对不要硬编码盘符路径，保证源码在团队成员间分发或迁入 CI/CD 流水线时即拷即用。
3. **扇区擦除保护机制**：
    在编写 Flash 擦写底层时，务必结合 `IS_ADDR_IN_APP_A()` 等宏校验写入范围，杜绝由于指针越界直接误擦 Sector 5（Boot Param）或 Sector 0~4（Bootloader 自身）。
